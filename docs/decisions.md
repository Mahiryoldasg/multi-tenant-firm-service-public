## Pre-build

- **2026-09-24 · Runtime** - Node 22/24 LTS, `engines >= 20.19`. Node 18/20 are EOL and better-sqlite3 12.x ships prebuilt binaries for Node 20-26 (contract note N1).
- **2026-09-24 · HTTP framework** - Express 5. We own the 401→403→404→400→409 pipeline; schema-first frameworks validate before the handler and would answer 400 before 404.
- **2026-09-24 · Imports** - relative imports use the real `.ts` extension; `tsc` rewrites them (`rewriteRelativeImportExtensions`). Same code runs under tsx, Vitest and compiled Node.
- **2026-09-24 · Single package** - server and UI share one `package.json` so `npm install && npm start` is the whole setup; Vite builds the UI into `dist/web`, Express serves it.
- **2026-09-24 · Env bootstrap** - `scripts/ensure-env.mjs` creates `.env` and a random `JWT_SECRET` on first run, so a clean machine needs no manual step and no secret is committed.
- **2026-09-24 · Line endings** - `.gitattributes` forces LF so Windows checkouts lint and format the same as Unix.
- **2026-09-24 · Vitest 4.0.18 pin** - Vitest 4.1.x makes npm 10.9 (bundled with Node 22) crash while resolving dependencies (`Cannot read properties of null (reading 'edgesOut')`), so a clean `npm install` on Node 22 would fail. 4.0.18 installs cleanly on npm 10 and 11.
- **2026-09-24 · allowScripts** - npm 11 warns about install scripts that are not listed in `allowScripts`. better-sqlite3 needs its install script to fetch the prebuilt binary, so it is allowed explicitly (plus esbuild). `@scarf/scarf` (swagger-ui telemetry) is denied.

## Feature 1 - Persistence & idempotent seed

- **2026-09-25 · SQLite connection** - `openDatabase` creates the `DB_PATH` folder, then enables `journal_mode=WAL` and `foreign_keys=ON` before migrating. better-sqlite3 does not create folders (a fresh clone has no `data/`), and SQLite keeps foreign keys off unless each connection turns them on.
- **2026-09-25 · Migrations** - ordered SQL strings tracked by `PRAGMA user_version`; each migration and its version bump share one transaction, and a committed migration is never edited. Strings, not `.sql` files, because `tsc` emits only TypeScript into `dist/server`.
- **2026-09-25 · Initial schema** - migration 1 creates the whole locked data model, including `display_tokens` and `firms.active_mode_id` (used from feature 7), because features 2-13 depend on these shapes.
- **2026-09-25 · NOT NULL primary keys** - every TEXT primary key is declared `NOT NULL`, because SQLite otherwise accepts NULL in any primary key that is not `INTEGER PRIMARY KEY`.
- **2026-09-25 · Password hashing** - async `node:crypto` scrypt with a 16-byte salt and a 64-byte key, stored as `<salt>:<key>` hex and compared with `timingSafeEqual`; async so request handlers never block the event loop. Node's default cost (N=16384, r=8, p=1) keeps logins and tests fast; OWASP suggests more, and raising it later needs a format version or a reseed.
- **2026-09-25 · Seed config** - the 8 `SEED_*` values are required on every boot, with no defaults in code: they are credentials, the contract keeps secrets out of code, and a broken `.env` fails at once. `.env.example` holds the documented values.
- **2026-09-25 · Idempotent seed** - a `meta` marker (`seeded_at`), not row counts, records the seed, so deleting the seed firms never re-seeds. Passwords are hashed before the synchronous better-sqlite3 transaction; one `BEGIN IMMEDIATE` transaction re-checks the marker and inserts everything, so a failed seed leaves nothing behind. Exactly 2 firms.

## Feature 2 - Error contract & login

- **2026-09-25 · Error envelope** - handlers throw `HttpError(code, message)` and one central error handler writes every `{ error: { code, message } }` body. Status comes from the code, so a handler cannot pair a contract code with the wrong status, and no route builds an error body by hand.
- **2026-09-25 · Unknown routes** - a final fallback answers `404 NOT_FOUND` for any path and method, with no `405`: the contract's code list has no 405.
- **2026-09-25 · Unreadable bodies** - every http-errors client error (a 4xx `status` with `expose: true`) becomes `400 VALIDATION_ERROR`. That covers all body-parser errors: malformed JSON, over 100 kB, an unsupported charset or encoding, and a corrupt compressed body, which has no `type` (F-02). The contract has no 413 or 415, and its 400 covers a broken body. These errors are not logged: they carry the raw request text, which can hold a password. Express's router `URIError` for a malformed percent-encoded param has no `expose` and stays a 500 until features 4 and 6 choose 400 or 404 for it.
- **2026-09-25 · INTERNAL_ERROR** - an unexpected failure answers `500` with code `INTERNAL_ERROR` and a generic Turkish message, and logs the details. The contract defines no server-error code, so this is a marked extension that keeps the envelope shape the same everywhere.
- **2026-09-25 · Token lifetime** - `USER_TOKEN_TTL` accepts only `<n>s|m|h|d`, fails at boot otherwise, and is passed to `jsonwebtoken` as whole seconds. jsonwebtoken reads a bare numeric string such as `"3600"` as milliseconds, which would silently issue 3.6-second tokens.
- **2026-09-25 · Login validation** - login checks only that `email` and `password` are non-blank strings (`400`); there is no email format check. A malformed email matches no one and gets the ordinary `401`, and login stores nothing that a format rule would protect.
- **2026-09-25 · Identical login failure** - an unknown email, a wrong password, a deleted user and a deleted firm all get the same `401` body. An unknown email is still checked against a dummy scrypt hash, so response time does not reveal which emails exist either.
- **2026-09-25 · Credential lookup** - login finds users through `findActiveUserByEmail` in `modules/platform`, which excludes deleted users and users of deleted firms in SQL. Feature 4's firm delete will also soft-delete the firm's users; the firm check keeps login correct without relying on that cascade.
- **2026-09-25 · Platform admin firmId** - the login response and the token omit `firmId` for the platform admin instead of sending `null` (contract §2: "platform_admin'de firmId yoktur").
- **2026-09-25 · Email normalization** - `normalizeEmail` (trim + lower-case) is the single rule behind `email_normalized`, shared by the seed and login now and by employee writes in feature 6, so stored and looked-up emails can never disagree.

## Feature 3 - Request authentication

- **2026-09-26 · Authentication order** - `authenticate` is mounted on `/api` right after the public `POST /api/auth/login`, so every other `/api` path, including unknown paths and wrong methods, answers `401` before `404`. The body parser runs first, so unparseable JSON stays `400`, which the contract allows.
- **2026-09-26 · Role and firm from the DB** - every request re-reads the user by the token's `sub`, and `req.auth` takes role and firm from that row; the token's `role` and `firmId` claims are never read. A role change applies on the next request and a deleted user gets `401` without any token blacklist (contract §2).
- **2026-09-26 · Deleted firm check** - `findActiveUserById` excludes users of a soft-deleted firm in SQL, like the email lookup, so a deleted firm's user tokens fail even if feature 4's cascade ever misses a user row.
- **2026-09-26 · One pinned verify** - `verifyToken` is the only JWT verification and pins `algorithms: ['HS256']`, so a token cannot choose `none` or another HMAC with our secret. jsonwebtoken errors become "invalid", and so does the raw `SyntaxError` jws throws when a `typ: 'JWT'` header comes with a non-JSON payload, because it parses the payload before any signature check (F-04). Anything else stays a `500`. Feature 8's socket handshake reuses it.
- **2026-09-26 · User vs display token** - any `kind` claim means "not a user token": `kind: 'display'` gets `401` with its own message, and any other `kind` or a non-string `sub` gets the invalid-session `401`. The kind check comes before the DB lookup, so a display token stays rejected on HTTP even if it ever carried a user's `sub`.
- **2026-09-26 · Bearer parsing** - the header must be `Bearer` (case-insensitive, as RFC 7235 defines auth schemes), one or more spaces, and exactly one token; anything else is `401`.
- **2026-09-26 · /api/auth/me shape** - `200 { user: { id, email, role, firmId? } }`, the same object as login's `user`, built by one `toUserResponse` so the two cannot drift (contract note N6). It adds no firm name or other extras.
- **2026-09-26 · req.auth and getAuth** - `req.auth` holds `{ userId, email, role, firmId }` from the row read during authentication, so `/me` needs no second read. `getAuth(req)` throws, giving a `500`, when a route runs without `authenticate`, so a mis-mounted route fails closed instead of running anonymously.
- **2026-09-26 · 401 messages** - three short Turkish messages: missing credentials, invalid or expired session, and display token. None says whether a user or firm exists, and a DB failure is a `500`, never a `401`.
- **2026-09-26 · Logger destination** - `createLogger` takes an optional destination stream (stdout by default) only so a test can prove that the real redaction writes the `Authorization` header as `[redacted]`.

## Feature 4 - Firm management

- **2026-09-26 · Platform-admin guard** - `requirePlatformAdmin` is mounted together with the firm router on `/api/firms`, so every method and subpath there, including unknown ones, answers a firm user `403` before any `404`. It reads the role `authenticate` loaded from the DB. Express matches the prefix by whole path segment, so `/api/firmsx` is not guarded.
- **2026-09-26 · Firm code in modules/platform** - firm SQL and routes live in `modules/platform`, next to credential lookup. The `:id` is the platform admin's target resource, so the delete cascade's `firm_id = @id` is platform code, not tenant scoping.
- **2026-09-26 · Firm list order** - oldest first by `created_at`, then `rowid`, so firms created in the same instant (the seed) keep their insertion order. The contract fixes no order; this one is stable for the UI and the tests.
- **2026-09-26 · Atomic create** - the admin password is hashed before the synchronous transaction; one `BEGIN IMMEDIATE` transaction pre-checks the email and inserts the firm and its admin. A `SQLITE_CONSTRAINT_UNIQUE` that escapes it is also a `409`, mapped outside the transaction because returning from inside a better-sqlite3 transaction function would commit the firm row.
- **2026-09-26 · Pre-check vs unique index** - the pre-check reuses `findActiveUserByEmail`, which skips users of deleted firms, while the partial unique index still counts them. Such a row exists only through direct SQL, since the delete cascades; the constraint mapping answers it with `409`, and the tests use it to prove that safety net.
- **2026-09-26 · Admin email and trimming** - `adminEmail` must have the light `local@domain`, no-whitespace shape (`isValidEmail`), otherwise `400`; login still has no format check. `name` and `adminEmail` are stored and returned trimmed, the email in its original casing, and the password is hashed untrimmed.
- **2026-09-26 · Shared body validation** - `parseBody` and `requiredString` in `http/validate.ts` replace login's hand-written parsing, so every handler turns the first Zod issue into its `400` message the same way.
- **2026-09-26 · Seed reuses the inserts** - the seed calls `insertUser` and `insertFirmWithAdmin` from `modules/platform`, so it and `POST /api/firms` cannot write different rows. These plain inserts leave conflicts to the caller, so a clashing seed still fails with the raw unique error and rolls back.
- **2026-09-26 · Cascading soft delete** - one `BEGIN IMMEDIATE` transaction stamps the firm and its active users with the same time, which frees their emails; users deleted earlier keep their own `deleted_at`. A repeated `DELETE` or a `PATCH` of a deleted firm is `404` (contract §3). Display tokens and the active mode stay; feature 8 disconnects the firm's sockets after the commit.
- **2026-09-26 · Malformed id** - the router's `URIError` for an invalid percent-encoded param (`/api/firms/%E0`) answers `404 NOT_FOUND`. It is raised after the auth guards while matching `:id`, no resource can have that id, and `404` comes before `400` in the check order. This settles the choice the feature 2 note left open, for feature 6's `:id` routes too.
- **2026-09-26 · Redaction** - `*.adminPassword` joins the redact paths next to `*.password`; nothing logs request bodies today, and a test proves the admin password never reaches the log.
- **2026-09-26 · Swagger later** - no OpenAPI registry exists yet, so the firm routes get their Swagger entries with the full contract in feature 10. Their Zod body schemas are module-level constants for it to register.
- **2026-09-26 · Nested router 404** - a nested `express.Router` answers an unhandled `OPTIONS` itself with `200` and an `Allow` header when no error is pending (F-04). The firm router therefore ends with `router.use(notFoundHandler)`, so every unhandled request stays on the `404` envelope (no `405`); the tenant routers of features 5 and 6 must end the same way.

## Feature 5 - Tenant scope layer

- **2026-09-26 · Tenant scope** - `createTenantScope(db, firmId)` returns firm-bound repositories, starting with the employee reads `list()` and `findById(id)`; features 6 and 7 add the writes, `mode` and `displayTokens` to the same scope. The firm is captured when the scope is built and no method takes a firm id, so a handler cannot ask for another firm's rows. Another firm's, a deleted, an unknown and the platform admin's id all give `undefined`, which later routes answer with the same `404`.
- **2026-09-26 · tenancy folder** - the scope and its SQL live in `src/server/tenancy/`, outside `modules/tenant/`. The lint rule then covers the whole tenant module with no exception, and `firm_id = @firmId` is written in one folder only.
- **2026-09-26 · Firm from the DB** - `requireTenant` binds the scope to `getAuth(req).firmId`, the firm `authenticate` read from the user row on this request. The token's `firmId` claim, route params, the query, headers and the body are never used; a test signs a token whose claim names the other firm and still gets the caller's own firm.
- **2026-09-26 · Prefix guard** - `requireTenant` is one `app.use` on `/api/employees`, `/api/mode` and `/api/display-tokens`, after `authenticate` and before any tenant router. A caller without a firm, which the users `CHECK` makes exactly the platform admin, gets `403` on every method and subpath there, before any `404` or `400` (contract §3 "tüm metotlarıyla"). It reuses the platform guard's message. Express matches the prefix by whole segment, so `/api/modex` is not guarded. Until features 6 and 7 mount their routers after the guard, a firm user there gets `404`; those routers end with `router.use(notFoundHandler)` like the firm router.
- **2026-09-26 · Scope per request** - the guard builds a new scope on every request. Building one runs no query, since each method prepares its statement when called, as the platform repositories do.
- **2026-09-26 · Employee list order** - oldest first by `created_at`, then `rowid`, like the firm list, so the seed admin comes first and employees created in the same instant keep their insertion order. The contract fixes no order.
- **2026-09-26 · getTenant** - tenant handlers read the scope only through `getTenant(req)`. Like `getAuth`, it throws, giving a `500`, when a route runs without the guard, so a mis-mounted tenant route fails closed.
- **2026-09-26 · Lint boundary** - a core `no-restricted-imports` rule on `src/server/modules/tenant/**` rejects `better-sqlite3`, any `db` module and any `platform` module from any folder depth, including type-only imports and `export ... from`, and fails `npm run lint`. A test runs the real config on probe code. The rule is a guardrail against accidental access, not a sandbox: it sees only static import declarations, so a dynamic `import()`, Node's own `node:sqlite`, or a handle typed through an allowed module's types (such as `Parameters<typeof createTenantScope>[0]`) would slip past it (F-04). The backstop is `app.ts`, which mounts tenant routers without a `db` dependency, so tenant code never holds a handle to misuse.
- **2026-09-26 · Swagger later** - the `403` on the firm-context prefixes gets its Swagger entry with those paths in feature 10, as the firm routes do.

## Fix - File errors and backend path casing

- **2026-09-26 · Body errors by origin** - `jsonBodyParser` wraps `express.json()` and turns its client errors into `400 VALIDATION_ERROR` where they arise, still unlogged (F-03). The error handler used to recognise body errors by shape alone (any exposed 4xx), which also caught `send`'s file errors. This narrows the Feature 2 "Unreadable bodies" note: the 400 now covers request bodies only.
- **2026-09-26 · File errors keep their status** - any other exposed 4xx error comes from a file response: `send`'s `412` for a failed `If-Match` or `416` for an unsatisfiable `Range`, behind `express.static` or the SPA fallback's `res.sendFile`. No contract code fits and these are UI paths, so the handler answers the way `send` answers its own errors: the error's status and headers (`Content-Range`), none of the file's headers, no body, nothing logged. Express's default error page was not used because it prints the stack trace unless `NODE_ENV` is `production`, and `npm start` does not set it.
- **2026-09-26 · Backend paths in any letter case** - `isBackendPath` lower-cases the path before its prefix checks, because Express routes case-insensitively: `/API/MODE` reaches the `/api` guards, so it must also skip the SPA fallback and get the `404` envelope instead of the UI page (F-06).

## Feature 6 - Employee management

- **2026-09-27 · Shared email conflict** - `EMAIL_TAKEN` and its `409` message moved from the firm code to `auth/email.ts`, next to the normalization rule. Firm and employee writes return and answer an email clash the same way, and the tenant router can reach them without importing platform code.
- **2026-09-27 · tenancy reuses platform user primitives** - `tenancy/employees.ts` calls `findActiveUserByEmail` and `insertUser` from `modules/platform/users.ts`. Email uniqueness is system-wide (contract §3), so employee and firm writes must share one definition of "taken" and one insert, as the seed already does. This narrows the "platform serves auth and the platform routes" standard to the tenant module: the lint rule still keeps `modules/tenant/**` free of platform, db and driver imports, and handlers still reach data only through `req.tenant`.
- **2026-09-27 · Write guard before routing** - the employee router runs `requireFirmAdmin` as its first middleware for `POST`, `PATCH` and `DELETE`, not per route. Express decodes `:id` while matching, so a per-route guard would answer a member's write to `%E0` with `404` before `403`. A member therefore gets `403` for any write under `/api/employees`, including unknown subpaths; `PUT` and `OPTIONS` have no route and stay `404` for everyone.
- **2026-09-27 · requireFirmAdmin** - a plain middleware beside `requirePlatformAdmin`, reading the DB role of the request, instead of the plan's `requireRole('firm_admin')` factory, which would have one caller. Feature 7 reuses it on its `POST` routes.
- **2026-09-27 · Firm liveness recheck** - the create handler awaits scrypt between authentication and the insert, so `create` checks inside its transaction that the firm is still active and otherwise inserts nothing (`FIRM_GONE`, answered `401` like the caller's next request). An active user of a deleted firm would keep its email taken in the unique index for good, against the contract's "a deleted firm's emails are reusable". The caller's own deletion or demotion during the hash is not rechecked: the request was authorized when it started, like any request in flight, and it leaves no broken row.
- **2026-09-27 · PATCH order and merge** - the scoped lookup runs before Zod, so another firm's or a deleted employee is `404` even with an invalid body (contract §3), then `400`, then `409`. The conflict check skips the employee's own row, so their own email in a new casing is stored as sent. The changes are merged over the current row in one `BEGIN IMMEDIATE` transaction with the check.
- **2026-09-27 · Role values** - `role` must be exactly `firm_admin` or `member` on `POST` and `PATCH`, never trimmed, so `platform_admin`, a blank or a padded value is `400`.
- **2026-09-27 · Ignored PATCH fields** - `PATCH` accepts only `email` and `role`. `password` (no password change is required) and `firmId` (the firm comes only from the DB) are dropped like any unknown field; a body with only those is `400`.
- **2026-09-27 · No self protection** - a firm admin may demote or delete any employee of their firm, themselves and the last firm admin included (contract note N2). The change applies on their next request: `403` on writes after a demotion, `401` after a deletion.
- **2026-09-27 · Employee soft delete** - one firm-bound `UPDATE` sets only `deleted_at` and `updated_at`, which frees the email and invalidates the token and login. An unknown, other-firm or already deleted id is `404`, so a repeated `DELETE` or a `PATCH` after it is `404` (contract §3).
- **2026-09-27 · Swagger later** - the employee routes get their Swagger entries, with `GET /api/employees/:id` marked as an extension (N5), in feature 10. Their Zod body schemas are module-level constants for it to register.

## Fix - Non-object JSON bodies

- **2026-09-27 · Non-strict JSON parsing** - `jsonBodyParser` calls `express.json({ strict: false })`, so a valid JSON body that is not an object or array (`"x"`, `null`, `42`, `true`) reaches `authenticate` and the guards instead of failing in the parser before them (F-07). Contract §3 lets only unparseable JSON skip the `401 → 403 → 404 → 400 → 409` order, and these bodies parse. This narrows the Feature 3 "Authentication order" note: the parser's `400` now covers unparseable, oversized and corrupt bodies only.
- **2026-09-27 · Non-object bodies meet the schemas** - every handler that reads a body validates it with `parseBody` and a `z.object` schema, so a non-object body now gets `400` with `INVALID_BODY_MESSAGE` after the `401`, `403` and `404` checks. Public login has no guard, so a non-object login body is still `400`, now from its schema. No handler reads `req.body` any other way.

## Feature 7 - Active mode & display tokens

- **2026-09-27 · Mode and display token repositories** - `mode` (`get()`, `set(now, modeId)`) and `displayTokens` (`create(now, token)`) join `createTenantScope`, bound to the firm like `employees`. Each write is one statement that only touches an active firm: `set` returns `false` and `create` returns `undefined`, writing nothing, when the firm is gone, and the handler answers `401` like the employee create's `FIRM_GONE`. Neither handler awaits anything after `authenticate` checked the firm, so this is defense in depth, not a reachable race; the repository tests cover it.
- **2026-09-27 · Opaque modeId** - any string that is non-blank after trimming, stored and returned untrimmed, with no format or length rule beyond the JSON parser's 100 kB body limit (contract §3: the service need not know modes). A mode set changes only `active_mode_id` and `updated_at`. Posting the current value again is a `200` like any other; feature 8 relies on that for its unconditional broadcast.
- **2026-09-27 · Display token label** - optional; when sent it must be a string, blank included, and is stored exactly as sent, otherwise `400`, `null` included. Absent is `null`. It lives only in the `display_tokens` row: it is never put in the token and no route returns it yet.
- **2026-09-27 · Body optional for display tokens** - every field of `{ label? }` is optional, so a request with no body (which Express leaves `undefined`, as it does for a non-JSON content type) is parsed as `{}` and gets a token with no label. A JSON body that is not an object, `null` included, still gets `400`. This narrows the non-object-body fix: that one handler maps an absent body to `{}` before `parseBody`.
- **2026-09-27 · Display token claims** - HS256 with `JWT_SECRET`, exactly `{ kind: 'display', firmId }` plus `iat` and `jti`, with no `exp`, `sub` or `role` (contract §2). `jti` is the `display_tokens.id` it was issued as, kept for a future revoke (contract note N8); revoke itself is out of scope (contract §6). The token string is never stored or logged.
- **2026-09-27 · Token firm from the row** - the handler never handles a firm id: it signs the `{ id, firmId }` that `create` returns from the firm-bound insert, so the token's firm and `jti` are exactly what the row holds.
- **2026-09-27 · Issuer for audit only** - `created_by_user_id` comes from `getAuth(req)`, the caller read from the DB, never from the body. It never affects validity: a token outlives its issuer's deletion or demotion and dies only with its firm (contract §2), which feature 8 enforces at the handshake.
- **2026-09-27 · Per-route write guard** - `POST /api/mode` and `POST /api/display-tokens` run `requireFirmAdmin` as route middleware. The employee router guards before routing only because Express decodes `:id` while matching; these routes have no `:id`, so a member still gets `403` before any `400`. Other methods and subpaths, such as `PUT /api/mode` or `DELETE /api/display-tokens/x`, have no route and stay `404` for every firm user.
- **2026-09-27 · Broadcast in feature 8** - `POST /api/mode` only stores and answers here. Feature 8 adds `broadcastModeChange` right after the one successful `set`, the handler's single success point; no emitter stub was added.
- **2026-09-27 · Swagger later** - the mode and display token routes get their Swagger entries in feature 10. Their Zod body schemas are module-level constants for it to register.

## Fix - Spread order in firm-bound inserts

- **2026-09-27 · Repository values bound last** - when a repository spreads a caller's object into bound SQL parameters or an insert helper, the spread comes first and the repository's own `id`, `firmId` and `now` come last, as `insertUser` already did (F-01). Later keys win, and TypeScript rejects extra keys only on a fresh object literal, so a caller object carrying a stray `firmId` could otherwise write a display token or an employee into another firm while the scope still reports its own. No caller can pass such a key today, but the scope's "no method takes a firm id" guarantee must hold in the repository itself. The display token insert and the employee create now follow the rule, and a regression test for each proves a stray `firmId` is ignored.

## Feature 8 - Realtime mode channel

- **2026-09-27 · Handshake check** - `io.use` accepts only a `handshake.auth.token` that verifies as HS256 with `JWT_SECRET`, has `kind: 'display'`, a string `firmId`, no `sub` or `role`, and names a live firm (contract §2, §4). Anything else is `next(new Error(message))`, which the client sees as `connect_error`. The `jti` is not looked up, since revoke is out of scope (§6, N8), and the issuer's deletion or role change does not matter.
- **2026-09-27 · Rejection messages** - three Turkish messages, mirroring HTTP: no token (`Display token gerekli.`), a user token (`Socket bağlantısı yalnız display token ile yapılabilir.`), and every other failure (`Display token geçersiz.`). A deleted or unknown firm shares the invalid-token message, as a deleted firm's user does on HTTP. No `data` field: the contract names only `connect_error`. The feature 13 simulator shows the message.
- **2026-09-27 · Handshake errors** - Socket.IO runs middleware without a `try/catch`, so an unexpected error inside the check (a closed DB, a non-JWT error that `verifyToken` rethrows) would escape into its event handling. The check catches it, logs it without the handshake `auth`, and rejects with the generic `Beklenmeyen bir hata oluştu.`
- **2026-09-27 · Room from the firm row** - a socket joins `firm:<id>` on `connection`, with the id of the firm row the check read, never the raw claim. The server registers no client event listeners and only the main namespace exists, so a display cannot join another room or relay an event; a test emits `join` and `mode-change` to prove it.
- **2026-09-27 · Synchronous handshake** - the check stays synchronous (better-sqlite3 is). Socket.IO connects the socket one `process.nextTick` after the middleware chain, so no HTTP request, such as a firm delete, can run between the live-firm check and the room join.
- **2026-09-27 · Display channel on the scope** - `req.tenant.displays.broadcastModeChange(modeId)` is bound to the scope's firm like the repositories, so the mode handler never handles a firm id and cannot reach another firm's room. `createTenantScope` takes the realtime server as a third parameter; `broadcastModeChange(firmId, modeId)` in `realtime/` stays the only emitter of `mode-change`.
- **2026-09-27 · Unconditional broadcast** - `POST /api/mode` emits `{ modeId }`, exactly as stored (untrimmed), after the one successful `set` and before the `200`; a repeated value emits again (contract §4). A failed request (`401`, `403`, `400`) emits nothing, and nothing is pushed on connect (contract §6, N4).
- **2026-09-27 · Disconnect on firm delete** - after `softDeleteFirm` commits, `DELETE /api/firms/:id` calls `disconnectSockets(true)` on the firm's room (contract note N3). Socket.IO 4.8 sends each display a disconnect packet and then closes the connection, so the client sees `io server disconnect` and does not retry by itself; a new connection fails the live-firm check with `connect_error`. A `404` delete disconnects nothing.
- **2026-09-27 · Attach and shutdown** - `index.ts` attaches Socket.IO after `createServer(app)`, so engine.io hands every non-socket path to Express. Shutdown goes through `io.close()`, which closes the display sockets and then the HTTP server; `server.close()` alone would wait for open websockets until the 5 s forced exit.
- **2026-09-27 · Socket.IO options** - `serveClient: false`, since the UI bundles `socket.io-client`, and typed server events pin the `mode-change` payload to `{ modeId: string }`. No CORS options: the UI reaches `/socket.io` on its own origin (Express in production, the Vite proxy in development), and Node clients are not subject to CORS.
- **2026-09-27 · Delivery barrier in tests** - a test proves a display did not get an event by then sending it one it must get: Socket.IO keeps order per connection, so a leaked event would have arrived first. No sleeps. Displays record their events from before they connect, so a push on connect would be caught.
- **2026-09-27 · Later features** - the 2+ clients per firm leak matrix and the wider invalidation cases belong to feature 9, and the Swagger text for the socket channel to feature 10.

- **2026-09-29 · No disconnect on employee delete, role change or expiry** - the handshake is the only check on an open control socket. That is safe because the socket carries no data: the refetch after the next signal gets `401`, the session ends and the hook closes the socket, and a reconnect fails the handshake. A hand-written client of a deleted user could still learn that (not what) the mode changed until it disconnects; recorded as a DESIGN.md trade-off.
- **2026-09-29 · Refetch on every connect** - no signal covers a change made while the channel was down, or between the panel's first `GET` and the join, so each (re)connect invalidates `['mode']`. The first connect therefore costs one more `GET`.
- **2026-09-29 · Leak test on shared connections** - a payload-free signal cannot tell a leaked event from the barrier, so in `socket-leak.test.ts` each control client shares one `Manager` with a display. The display gets a broadcast's event before its control twin, so the signal count taken when the display gets the barrier is exact. A one-off mutation (emitting to the whole `/control` namespace) failed the test with `[8, 8]` instead of `[4, 4]`.
- **2026-09-29 · Status line and live value** - the mode panel shows the channel state as plain text (connecting, live, retrying, or closed with the server's reason), not announced, since the page still works over HTTP without it. The value sits in an always-rendered `aria-live="polite"` region, so a change from another screen is announced.
- **2026-09-29 · Browser check** - on `npm start`, three Playwright tabs (an Acme admin, an Acme member, a Globex admin): the member's tab showed the admin's change about 0.6 s later without focus or reload, Globex did not change, and a server restart showed "koptu", then "açık" with one refetch of the mode. ## Feature 18 - On-demand display mode sync

- **2026-09-29 · Still no push on connect** - a display asks with `mode:get` instead of the server sending the mode when it connects. An unsolicited event could break "exactly one event" or "no event" assertions in contract tests, and a client that never asks sees the contract channel exactly as before; the "pushes nothing when a display connects" test passes unedited.
- **2026-09-29 · The answer is the `GET /api/mode` body** - the ack is `{ modeId }`, the stored value untrimmed, or `{ modeId: null }` when no mode was ever set, so a display and the HTTP API read the same shape. No new event name or payload is added for displays.
- **2026-09-29 · Ack last, no ack ignored** - Socket.IO passes the client's ack as the last argument, so the listener takes `args.at(-1)` and ignores everything before it. A request without a function there gets no reply and no log, and the socket stays connected: calling a missing ack would throw inside the listener, and a request that cannot be answered is not an error worth logging.
- **2026-09-29 · Firm from the handshake, through the scope** - the listener reads `createTenantScope(db, socket.data.firmId, realtime).mode.get()`, with the firm row id the handshake fixed, so the firm filter stays in the tenancy repositories and no argument can name another firm (a test sends another firm's id and still gets its own mode). There is no per-request re-check: the handshake stays the socket's trust point, as for `mode-change`, and a deleted firm's displays are disconnected synchronously right after the delete commits.
- **2026-09-29 · Failure answers the 500 envelope** - an unexpected error is logged as `Mode request failed` (with the error, never the handshake) and answered `{ error: { code: 'INTERNAL_ERROR', message } }`, the envelope HTTP uses for a `500`, so a display can tell a failure from a firm without a mode. Only the listener catches; the read itself is unchanged.
- **2026-09-29 · Order from a synchronous listener** - the listener reads and acks in one synchronous call, as `POST /api/mode` stores and broadcasts in one. On one connection the ack and any `mode-change` therefore arrive in the order the mode changed, and the simulator simply keeps whichever arrives last.
- **2026-09-29 · Simulator asks on every connect** - `openDisplayConnection` sends `mode:get` on each `connect`, automatic reconnects included, with a 5 s timeout (`MODE_SYNC_TIMEOUT_MS`, a parameter only so a test can shorten it). A timeout and an unexpected answer get fixed Turkish reasons; an error envelope shows its own message. `modeId` and reasons render as React text only.
- **2026-09-29 · Failures after a close are dropped** - socket.io-client 4.8 fails every pending timeout ack with "socket has been disconnected" when the connection closes, `close()` included. A `socket.connected` check alone drops those: `disconnect()` clears `connected` before it fails the acks, and a closed socket never connects again, so no separate `closed` flag is needed. A one-off mutation (removing the check) failed exactly the two close tests against a stub server.
- **2026-09-29 · Browser check** - on `npm run dev`, Playwright on `/display`: an Acme token showed its stored mode at once with a `mode:get yanıtı` log line; a temporary firm created for the check showed "Bu firma için henüz bir mod seçilmemiş.", and deleting it showed the server's close with no extra sync failure. The temporary firm was deleted again; two display tokens labelled "feature 18 check" remain in the local database.
- **2026-09-29 · README test list** - the README lists only `tests/isolation/`, so `mode-get.test.ts` (in `tests/realtime/`) gets its own sentence under the list instead of a list line; the leak suite's line names the new two-firm case.
- **2026-09-29 · Diagram shows `mode:get`** - this supersedes feature 16's "no P2 items" for `mode:get`: the Socket.IO box says the server answers only the displays' `mode:get` and still sends nothing on connect, and the legend names it as a request next to the two events. The PNG was re-exported with the same command and is about 2.2 MB.

## Feature 19 - Device pairing flow (design only)

- **2026-09-29 · Design only, no code** - a DESIGN.md write-up is enough for this bonus, so the flow is a proposal in its own section; no route, table, UI or Swagger entry exists for it on `main`.
- **2026-09-29 · Device-initiated, RFC 8628 shape** - the display starts pairing and shows a code, a firm_admin approves it in the control UI, and the display then collects its token. Displays are kiosks that cannot log in, so the kiosk never takes input; the typing happens on the admin's logged-in screen.
- **2026-09-29 · The short code is not a credential** - `userCode` (8 characters, 10 minutes, single use) is accepted only from an authenticated firm_admin; the public side's only secret is the 256-bit `deviceCode`. A guessed code can at most pull a pending screen into the guesser's own firm, which leaks nothing and shows up as a `404` for the real admin. The rejected alternative, a code the admin creates and types on the device, would make the short code a bearer credential on a public endpoint.
- **2026-09-29 · Only `deviceCode` is hashed** - SHA-256 is enough for a 256-bit random value. `user_code` is stored plain: it is short-lived and useless without an admin session.
- **2026-09-29 · Approval through the tenant scope** - the firm comes from `req.tenant` through a proposed firm-bound `displayPairings` repository, and the `display_tokens` row is written with the existing `displayTokens.create`. Delivery signs with the existing `signDisplayToken`, so the contract's display claims, the handshake, the rooms and the invalidation on firm delete apply unchanged.
- **2026-09-29 · Single delivery, codes in bodies** - the token is handed out once, and a lost response means pairing again; that limits who can hold a token with no `exp`. Both codes travel in request bodies, since pino-http logs URLs but not bodies.
- **2026-09-29 · Mermaid in DESIGN.md** - the sequence diagram is a Mermaid block instead of a draw.io file: it diffs as text, GitHub renders it, and no authoring tool is needed. Mermaid 11 rendered it without an error in the Playwright browser (on `about:blank`, since `file:` is blocked there); GitHub's rendering was not viewed.
- **2026-09-29 · Architecture diagram unchanged** - the flow is not built, and the diagram shows only what exists on `main` (feature 16).
- **2026-09-29 · No tests** - no code changed. The link guard in `tests/readme.test.ts` already covers the edited DESIGN.md and `docs/README.md`.
